# 정확성 개선 명세서

## 목적

이 문서는 DART EBITDA Analyzer의 정확성을 높이기 위해 선행 점검에서 발견한 8개 문제를 정리하고, 각 문제의 원인, 리스크, 수정 방향, 완료 조건을 정의한다.

앱의 최우선 목표는 "값을 많이 채우는 것"이 아니라 "원문에서 검증 가능한 값을 정확히 추출하고, 불확실한 값은 불확실하다고 표시하는 것"이다.

## 공통 원칙

- 최종 숫자는 반드시 원문 출처를 가져야 한다.
- AI는 가능하면 숫자 자체가 아니라 위치 선택과 판단 보조에 사용한다.
- 단위, 당기 컬럼, 연결/별도 범위가 불확실하면 조용히 통과시키지 않는다.
- 검증 통과, 검증 실패, 검증 불가를 명확히 분리한다.
- 실제 DART 보고서 fixture를 누적하여 회귀 테스트로 잠근다.

## 1. EBITDA가 실제로 계산되지 않는 문제

### 현재 문제

`SPEC.md`에는 EBITDA 공식이 정의되어 있지만, 앱의 결과 모델과 UI/Excel 출력에는 EBITDA 값이 없다. 현재는 EBITDA 계산에 필요한 영업이익, 감가상각비, 사용권자산상각비, 무형자산상각비를 각각 보여줄 뿐이다.

### 정확성 리스크

- 사용자가 앱 이름과 명세를 보고 EBITDA가 계산된다고 기대하지만 실제 최종 EBITDA가 없다.
- 사용권자산상각비가 감가상각비에 포함된 경우와 별도 공시된 경우를 구분하지 않으면 중복 계산 가능성이 있다.
- 합산 공시("감가상각비 및 무형자산상각비")를 EBITDA에 어떻게 반영했는지 추적하기 어렵다.

### 수정 방향

- 파이프라인 최종 단계에서 `EBITDA` 파생 항목을 계산한다.
- 기본 공식은 `영업이익 + 감가상각비 + 사용권자산상각비 + 무형자산상각비`로 두되, 아래 예외를 명시한다.
- 감가상각비가 "감가상각비 및 무형자산상각비" 합산액이면 무형자산상각비는 `None`으로 두고 합산액만 더한다.
- 사용권자산상각비는 원문에서 별도 행으로 분리 기재된 경우에만 더한다.
- EBITDA 계산에 사용된 구성요소와 제외 사유를 `ebitda_trace` 또는 동일한 구조의 메타데이터로 남긴다.

### 완료 조건

- UI 요약, 상세, Excel에 EBITDA 컬럼이 표시된다.
- 합산 공시와 분리 공시 케이스에서 중복 계산하지 않는다.
- EBITDA 구성요소가 하나라도 불확실하면 EBITDA 상태가 `verified`가 아니라 `partial` 또는 `unverified`로 표시된다.

## 2. AI가 숫자 최종값을 보정하는 문제

### 현재 문제

일반 재무항목은 Python 추출값과 AI 독립 추출값을 비교한 뒤, 불일치 시 AI 판정 결과가 최종값에 반영될 수 있다. 반면 감가상각 모듈은 AI가 위치만 고르고 Python이 숫자를 읽는 구조다.

### 정확성 리스크

- AI가 원문 숫자를 잘못 읽거나 단위를 잘못 환산해도 최종값으로 들어갈 수 있다.
- 최종값이 어느 표, 어느 행, 어느 컬럼에서 왔는지 구조적으로 검증하기 어렵다.
- 같은 보고서를 재분석했을 때 AI 응답 차이로 결과가 달라질 수 있다.

### 수정 방향

- 모든 재무항목 추출 결과를 단순 숫자에서 `value + source metadata` 구조로 확장한다.
- AI는 일반 재무항목에서도 가능하면 `table_id`, `row_id`, `column_id` 같은 위치를 반환하게 한다.
- Python은 AI가 지목한 위치의 실제 셀을 다시 읽고, 단위 변환까지 수행한다.
- AI가 숫자를 직접 반환하는 기존 경로는 fallback으로만 두고, 해당 결과는 `unverified_ai_value`로 표시한다.

### 완료 조건

- 최종값마다 `raw_value`, `unit_multiplier`, `statement`, `row_label`, `column_label`, `rcept_no`가 남는다.
- AI가 반환한 숫자만으로 `verified` 상태가 되지 않는다.
- Python 추출값과 AI 위치 선택값이 다르면 검증 플래그에 남는다.

## 3. 경로A DART API 추출의 재무제표 유형 필터 부족

### 현재 문제

DART `fnlttSinglAcntAll` 응답에서 `account_id` 또는 `account_nm`을 기준으로 첫 매칭을 사용한다. 하지만 항목별로 `sj_div`가 BS, IS, CIS, CF 중 어디인지 엄격히 제한하지 않는다.

### 정확성 리스크

- 같은 계정명 또는 유사 계정명이 다른 재무제표 영역에 있을 때 잘못 매칭될 수 있다.
- 손익계산서와 포괄손익계산서의 중복/대체 관계를 명확히 처리하지 못한다.
- account_id가 같은 행이 여러 개 나오는 경우 첫 번째 행 선택이 항상 맞는지 보장되지 않는다.

### 수정 방향

- 항목별 허용 `sj_div`를 명시한다.
  - BS 항목: `BS`
  - IS 항목: `IS`, 필요 시 `CIS`
  - CF 항목: 일반 재무 API에서는 직접 채우지 않고 전용 추출기 사용
- `account_id` 매칭 전에도 `sj_div`와 `fs_div`를 먼저 필터링한다.
- 같은 항목 후보가 여러 개면 우선순위와 충돌 로그를 남긴다.
- `account_nm` fallback은 완전 일치 또는 정규화 일치 중심으로 제한하고, 부분 포함 매칭은 낮은 신뢰도로 분류한다.

### 완료 조건

- 경로A 추출 로그에 선택된 `fs_div`, `sj_div`, `account_id`, `account_nm`이 남는다.
- 동일 항목 후보가 여러 개이면 조용히 첫 값을 쓰지 않고 후보 목록을 추적한다.
- BS/IS/CIS 혼재 케이스에 대한 단위 테스트가 추가된다.

## 4. 경로B XML 파싱의 연결/별도 범위와 섹션 경계 문제

### 현재 문제

감사보고서 XML 파싱은 직전 `TITLE`을 기준으로 BS/IS/CF/NOTES 섹션을 분류한다. 그러나 실제 감사보고서와 사업보고서는 연결/별도 재무제표가 혼재되거나, 주석 내부에 비슷한 제목이 반복되는 경우가 많다.

### 정확성 리스크

- 연결 기준으로 추출해야 하는데 별도 재무제표 표를 읽을 수 있다.
- 주석 안의 소제목이 재무제표 본문처럼 오인될 수 있다.
- 사업보고서 API 실패 후 본문 파싱 fallback 시 연결/별도 스코프가 약해질 수 있다.

### 수정 방향

- 일반 재무항목 추출에도 감가상각 모듈 수준의 스코프 해석 로직을 적용한다.
- `fs_div`를 `_extract_all_items()`에 전달하고, 연결/별도 범위에 맞는 테이블만 추출한다.
- TITLE 기반 분류가 실패하면 content 기반 fallback을 사용하되, fallback 결과는 낮은 신뢰도로 표시한다.
- 문서 전체가 연결 전용/별도 전용인지, 연결/별도 혼재인지 먼저 판별한다.

### 완료 조건

- 경로B 추출 함수가 `fs_div`를 입력받아 범위 필터링을 수행한다.
- 연결/별도 혼재 문서에서 다른 범위 테이블로 fallback하지 않는다.
- 선택된 표의 스코프가 결과 메타데이터에 남는다.

## 5. 컬럼/단위 추정 실패가 조용히 최종값이 되는 문제

### 현재 문제

당기 컬럼 탐지 실패 시 첫 번째 숫자 컬럼을 사용하고, 단위 탐지 실패 시 1원으로 가정한다. 어떤 경우에는 당기 컬럼의 값이 숫자가 아니면 0으로 처리한다.

### 정확성 리스크

- 전기 값을 당기 값으로 오인할 수 있다.
- 천원/백만원 단위를 놓치면 1,000배 또는 1,000,000배 오류가 발생한다.
- `-`, 빈칸, 0, 해당 없음, 파싱 실패가 구분되지 않는다.

### 수정 방향

- 컬럼 탐지 결과를 `current_col_confidence`로 기록한다.
- 단위 탐지 결과를 `unit_confidence`로 기록한다.
- 단위 감지 실패 시 기본값 1을 쓰더라도 결과 상태는 `unverified` 또는 `low_confidence`로 둔다.
- `-`는 무조건 0이 아니라 문맥별로 `zero`, `not_applicable`, `missing`, `parse_failed` 중 하나로 분류한다.
- 첫 번째 숫자 컬럼 fallback은 최종값으로 바로 확정하지 않고 검증 플래그를 남긴다.

### 완료 조건

- 모든 값에 사용한 컬럼 인덱스와 컬럼 라벨이 남는다.
- 단위가 원문에서 확인되지 않은 값은 `verified`가 되지 않는다.
- `0`과 `None`의 의미가 결과 구조에서 구분된다.

## 6. 검증 실패/스킵 정책이 너무 관대한 문제

### 현재 문제

필수 항목이 없어서 회계 항등식 검증을 스킵해도 `passed=True`로 처리된다. 최종 상태도 대체로 `ok`와 `error` 중심이라, "값은 일부 추출됐지만 검증 불가"인 상태가 명확하지 않다.

### 정확성 리스크

- 사용자가 검증 스킵을 검증 통과로 오해할 수 있다.
- 핵심 항목 누락이 있어도 성공 건수에 포함된다.
- 항등식 실패와 데이터 부족이 같은 UI 흐름에 섞인다.

### 수정 방향

- 검증 결과 상태를 최소한 아래처럼 분리한다.
  - `passed`: 검증 통과
  - `failed`: 검증 실패
  - `skipped_missing_data`: 필수 항목 누락
  - `not_applicable`: 해당 없음
- 전체 분석 상태도 `ok` 하나 대신 `verified`, `partial`, `unverified`, `failed_validation`, `error` 등으로 세분화한다.
- UI와 Excel에서 검증 스킵을 별도 색상/문구로 표시한다.

### 완료 조건

- 검증 스킵은 `passed=True`로 저장되지 않는다.
- 성공 건수와 검증 통과 건수가 명확히 분리된다.
- 필수 항목 누락은 사용자에게 플래그로 노출된다.

## 7. 감가상각 후보 필터와 AI 의존도 문제

### 현재 문제

감가상각 추출기는 구조적으로 가장 좋은 방향이지만, 주석 후보 필터가 완전하지 않다. 제외 키워드는 주로 헤더 일부와 섹션 제목에 의존하며, 제목 탐지가 실패하면 유형자산 변동표, 사용권자산 표, 판관비 표 같은 부분값 테이블이 후보에 남을 수 있다.

### 정확성 리스크

- 회사 전체 비용이 아니라 특정 자산군의 감가상각비를 EBITDA에 더할 수 있다.
- 판매비와관리비 내 감가상각비처럼 부분값을 전체값으로 오인할 수 있다.
- AI가 후보 중 잘못된 표를 선택하면 Python 검증은 숫자만 정확히 읽고 의미 오류는 놓칠 수 있다.

### 수정 방향

- 테이블 구조 기반 제외 규칙을 강화한다.
  - 취득원가, 감가상각누계액, 장부금액, 기초, 취득, 처분, 대체, 기말 등이 함께 있으면 자산 변동표로 분류
  - 판매비와관리비, 매출원가, 연구개발비 등 기능별 배분 표는 전체 비용 표와 분리
- "비용의 성격별 분류", "현금흐름표 조정", "영업에서 창출된 현금흐름" 같은 강한 긍정 시그널을 우선한다.
- AI 선택 전 Python이 후보별 `candidate_type`과 `risk_flags`를 붙인다.
- AI 선택 후에도 선택한 표의 `risk_flags`가 있으면 최종 상태를 낮은 신뢰도로 둔다.

### 완료 조건

- 감가상각 후보 테이블마다 `candidate_type`이 기록된다.
- 자산 변동표/누계액/판관비 표는 원칙적으로 AI 후보에서 제외된다.
- 감가상각 추적 로그에 후보 제외 사유와 선택 사유가 모두 남는다.

## 8. 테스트/명세와 실제 코드의 불일치 문제

### 현재 문제

현재 테스트는 자동 회귀 테스트라기보다 수동 진단 스크립트에 가깝다. 또한 `test_dart_connection.py`는 현재 `config.py`에 없는 `DART_API_KEY`를 import해 실패한다. `SPEC.md`에는 SQLite 결과 캐시가 있다고 되어 있지만 실제 구현은 확인되지 않는다.

### 정확성 리스크

- 기존에 맞았던 보고서가 나중에 깨져도 자동으로 알 수 없다.
- 문서와 실제 동작이 달라져 운영자가 잘못된 전제를 갖게 된다.
- 네트워크/API 상태에 의존하는 테스트만 있으면 추출 로직의 회귀를 잡기 어렵다.

### 수정 방향

- `tests/fixtures/`에 실제 DART XML 또는 익명화된 최소 XML fixture를 둔다.
- 주요 보고서 유형별 golden result를 만든다.
  - 상장사 사업보고서 경로A
  - 연결감사보고서 경로B
  - 별도 감사보고서 경로B
  - 연결/별도 혼재 사업보고서 본문 fallback
  - 감가상각 합산 공시
  - 감가상각/무형자산상각비 분리 공시
  - 단위 천원/백만원/억원 케이스
- 네트워크 테스트와 로직 테스트를 분리한다.
- `SPEC.md`를 실제 구현 기준으로 갱신하거나, 미구현 기능은 명확히 TODO로 표시한다.

### 완료 조건

- `pytest` 기반 단위/회귀 테스트가 추가된다.
- 네트워크 없이 핵심 파싱 로직 테스트가 가능하다.
- `test_dart_connection.py` import 오류가 수정된다.
- SPEC과 실제 UI/코드 동작이 일치한다.

## 권장 작업 순서

1. 결과 데이터 구조를 `value + source metadata + confidence` 형태로 확장한다.
2. EBITDA 계산 항목과 중복 방지 규칙을 구현한다.
3. 경로A `sj_div`/후보 충돌 필터를 강화한다.
4. 경로B 연결/별도 스코프 필터를 일반 재무항목에도 적용한다.
5. 단위/당기 컬럼 신뢰도와 검증 상태를 결과에 반영한다.
6. 검증 상태 모델을 `통과/실패/검증불가`로 분리한다.
7. 감가상각 후보 분류 규칙을 강화한다.
8. 실제 보고서 fixture 기반 회귀 테스트를 추가한다.

## 향후 구현 시 기준

새로운 추출 로직은 단순히 `float | None`을 반환하면 안 된다. 내부적으로는 반드시 아래 정보를 포함해야 한다.

```python
{
    "value": 1234567890.0,
    "raw_value": "1,234,567",
    "unit_multiplier": 1000,
    "normalized_value_unit": "KRW",
    "source": {
        "rcept_no": "20240318000000",
        "report_nm": "사업보고서 (2023.12)",
        "fs_div": "CFS",
        "statement": "IS",
        "table_id": "T12",
        "row_id": "R8",
        "row_label": "영업이익",
        "column_id": "C3",
        "column_label": "당기"
    },
    "confidence": "verified",
    "flags": []
}
```

UI와 Excel에는 사람이 읽기 쉬운 숫자를 보여주되, 상세 화면과 원본 시트에는 출처/신뢰도/플래그를 반드시 노출한다.
